# Роли оркестратора — простое описание

## Root / orchestrator

Это главный агент. Он не должен бездумно выполнять всю работу сам, если задача большая.

Он отвечает за:

- понимание реальной цели пользователя;
- разбиение задачи на части;
- выбор нужных subagents;
- определение, что можно делать параллельно;
- выдачу каждому агенту узкой и понятной задачи;
- сбор результатов;
- разрешение противоречий между агентами;
- финальную интеграцию и итоговый ответ.

Для Plus root работает на GPT-5.6 Luna с `max` reasoning.

## Explorer

**Задача:** понять, где именно в проекте находится нужная логика.

Он должен:

- найти релевантные файлы и символы;
- проследить реальный data/call flow;
- найти существующие тесты и конфигурацию;
- указать ограничения и риски;
- предложить минимальную поверхность изменений.

Он работает в `read-only` и не должен редактировать файлы.

Используйте его, когда перед кодингом сначала надо разобраться в чужом или большом проекте.

## Worker

**Задача:** выполнить конкретную ограниченную правку.

Он должен:

- работать только в заданном scope;
- делать минимально необходимое изменение;
- следовать существующим паттернам проекта;
- не устраивать побочные рефакторинги;
- не менять API, архитектуру, схемы и зависимости без явного разрешения;
- при необходимости добавить целевые тесты;
- выполнить локальную проверку результата.

Если задача внезапно требует более широкого решения, worker должен остановиться и сообщить root, а не расширять работу сам.

## Tester

**Задача:** независимо доказать, что изменение работает или не работает.

Предпочтительный подход:

- самый маленький тест, который реально проверяет поведение;
- существующие инструменты тестирования проекта;
- воспроизводимые шаги;
- точные ошибки и названия тестов.

Tester не должен переписывать production-код, чтобы тест «позеленел». Менять тесты он должен только если root прямо попросил это сделать.

## Researcher

**Задача:** проверить внешний технический факт.

Используется для:

- version-specific API;
- поведения библиотек и фреймворков;
- документации;
- зависимостей;
- фактов, которые опасно брать из памяти модели.

Researcher должен опираться на первичные источники и честно указывать версию, дату и неопределённость.

Он работает в `read-only`.

## Reviewer

**Задача:** независимая финальная проверка уже сделанных изменений.

Для Plus reviewer работает на GPT-6 Astra с `low` reasoning и в `read-only`.

Ищет в первую очередь:

- баги корректности;
- регрессии;
- security/permissions проблемы;
- риск потери или повреждения данных;
- race/concurrency ошибки;
- поломку API или обратной совместимости;
- недостающие важные тесты.

Он не должен редактировать код. Его задача — найти проблему и дать конкретный способ исправить или проверить её.

## Когда кого запускать

| Ситуация | Роль |
|---|---|
| Неясно, где нужный код | Explorer |
| Нужна конкретная правка | Worker |
| Нужно доказать, что всё работает | Tester |
| Нужна документация или проверка внешнего факта | Researcher |
| Нужна независимая финальная проверка | Reviewer |
| Нужно всё разложить и собрать вместе | Root / orchestrator |

## Как должна выглядеть хорошая делегация

Каждый subagent должен получить не абстрактное «почини проект», а контракт из шести вещей:

1. **Objective** — один конкретный результат.
2. **Scope** — какие файлы или подсистема входят в задачу.
3. **Context** — только нужный контекст.
4. **Constraints** — что нельзя менять.
5. **Deliverable** — что вернуть или реализовать.
6. **Acceptance criteria** — как проверить успех.

Чем уже задача агента, тем проще проверить его результат и тем меньше он расходует лишнего контекста.
