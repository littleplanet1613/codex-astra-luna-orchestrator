# Codex Astra + Luna Orchestrator — русская инструкция

Этот репозиторий настраивает Codex как команду из нескольких специализированных агентов.

Для профиля **Plus** главный агент работает на **GPT-5.6 Luna** с максимальным reasoning, а отдельные подзадачи выполняют специализированные Luna-агенты. Финальную независимую проверку делает **GPT-6 Astra reviewer**.

## Зачем это нужно

Вместо одного агента, который одновременно ищет код, пишет изменения, тестирует и сам себя проверяет, работа разделяется по ролям:

1. главный агент понимает задачу и делит её на части;
2. `explorer` изучает репозиторий и находит нужные файлы;
3. `worker` делает ограниченную правку;
4. `tester` проверяет результат;
5. `researcher` проверяет внешние факты и документацию;
6. `reviewer` независимо ищет ошибки после изменений;
7. главный агент собирает всё вместе и отдаёт итог пользователю.

Это особенно полезно для больших задач, затрагивающих несколько файлов, модулей или независимых направлений работы.

## Профиль Plus

| Роль | Модель | Reasoning | Доступ |
|---|---|---:|---|
| Root / orchestrator | GPT-5.6 Luna | max | workspace-write |
| Explorer | GPT-5.6 Luna | medium | read-only |
| Worker | GPT-5.6 Luna | medium | workspace-write |
| Tester | GPT-5.6 Luna | medium | workspace-write |
| Researcher | GPT-5.6 Luna | medium | read-only |
| Reviewer | GPT-6 Astra | low | read-only |

Главный принцип профиля Plus: **Luna делает основную работу, Astra тратится только на независимый review**.

## Когда использовать оркестратор

Подходит для:

- функции, затрагивающей несколько файлов;
- сложного бага, который надо трассировать по разным частям проекта;
- больших изменений в репозитории;
- задач, которые можно безопасно разделить на независимые части;
- работы, где полезно отдельно исследовать, реализовать, протестировать и проверить результат;
- задач, где вы прямо просите использовать subagents.

Для мелкой правки одного файла оркестратор обычно лишний: проще выполнить её одним агентом.

## Роли простыми словами

### `explorer`

Разведчик. Ничего не меняет. Находит нужные файлы, функции, зависимости, тесты и реальный путь выполнения кода.

### `worker`

Исполнитель. Получает узкую задачу и меняет только то, что входит в её границы. Не должен сам расширять объём работы или менять архитектуру без разрешения.

### `tester`

Проверяющий. Запускает минимальные тесты, которые реально доказывают или опровергают работу изменения. Производственный код не переписывает ради прохождения теста.

### `researcher`

Исследователь внешней информации. Проверяет документацию, версии API, поведение библиотек и другие факты, которые нельзя надёжно брать «из памяти».

### `reviewer`

Независимый ревьюер на Astra. Ничего не редактирует. Ищет реальные ошибки: регрессии, проблемы безопасности, целостности данных, совместимости, concurrency и недостающие важные тесты.

### Root / orchestrator

Главный координатор. Понимает цель, решает, кого запустить, распределяет задачи, собирает ответы, разрешает противоречия и формирует финальный результат.

Подробно: [`docs/ROLES_RU.md`](docs/ROLES_RU.md).

## Как пользоваться

После установки Codex может сам выбрать `astra-orchestrator`, если задача подходит под его описание.

Можно вызвать явно:

```text
$astra-orchestrator

Исправь экспорт счетов.
Сначала пусть explorer найдёт существующий путь,
worker внесёт минимальные изменения,
tester всё проверит,
а reviewer сделает независимый финальный review.
```

Необязательно писать роли каждый раз — это полезно только когда вы хотите явно задать порядок работы.

## Важное ограничение

Оркестрация расходует больше лимита, чем один агент: root остаётся в задаче всё время, а каждый subagent получает свой контекст. Поэтому не стоит запускать полную схему ради каждой мелкой правки.

Для Plus разумный режим:

- простая локальная правка → root-only;
- несколько файлов или сложная диагностика → orchestrator;
- независимый reviewer Astra → только когда это действительно полезно;
- параллельные агенты → только для реально независимых частей задачи.
